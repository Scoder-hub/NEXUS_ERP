> 通用 AI 协作规范，适用于各类开发环境与项目。  
> 优先级：`user_profile.md` > 本文件 > 项目级规则文件

v4.1 = v4.0 + **自我进化机制 2.0（可验证、可沉淀、可回归、可淘汰）+ 五维评价体系（带证据）+ 执行率/门槛治理**。

## 第零部分：新会话快速启动

> 每次新会话开始时，按以下顺序读取文件，5 步掌握项目全貌。

```
步骤 1 → 读 project_memory.md（或项目级 README/CLAUDE.md）
          了解：项目基本信息、进度、设计系统、角色提示词

步骤 2 → 读 docs/dev-tasks.md（或项目任务看板）
          了解：当前任务进度、阻塞信息、交接摘要、质量门槛执行情况
          判断：是否有进行中/阻塞的任务需要接手

步骤 3 → 读 docs/dev-notes.md（或项目知识库）
          了解：踩坑记录、延期决策、知识沉淀、质量保障体系、进化日志
          判断：当前任务涉及的模块是否有已知问题/已知风险

步骤 4 → 读 user_profile.md（如需团队规则细节）
          了解：完整的团队模式规则、角色边界、流程定义（跨项目权威）

步骤 5 → 读项目级规则文件（如 CLAUDE.md / AGENTS.md / .cursorrules）
          了解：代码级规范（命名、文件大小、安全红线）
```

**单角色模式**：如果用户指定了角色，直接跳到 project_memory.md 的"角色提示词"章节，按该角色的"首先做"列表执行。

## 第二部分：团队开发模式（v4.0 Gate + v4.1 执行率）

### 1. 总则
- **适用项目**：所有采用本协作规范的项目
- **审批规则**：仅 PRD 需要用户审批，审批通过后全流程自动流转，不再中断等待确认
- **执行机制**：用 Agent/Task 工具启动子代理扮演各角色，用任务看板跟踪状态

### 2. 规则文件优先级与同步

**优先级**（高→低，冲突时以高优先级为准）：

| 优先级 | 文件 | 职责 | 更新频率 |
|---|---|---|---|
| 1 | `user_profile.md` | 跨项目用户偏好 + 团队模式总规则 | 用户要求时 |
| 2 | 项目级规则（CLAUDE.md / AGENTS.md / .cursorrules 等） | 项目级代码规范和技术约束 | 技术栈变更时 |
| 3 | `project_memory.md` | 项目约定 + 角色提示词 | 项目决策时 |

**同步规则**：
- `user_profile.md` 是规则的**唯一权威源**，包含团队模式全部规则
- `project_memory.md` 中的角色提示词引用 user_profile.md 的规则，不重复定义
- 项目级规则文件只放代码级规范（命名、文件大小、安全红线），不放团队流程规则
- 修改规则时：先改 `user_profile.md`，再同步到其他文件的相关章节

### 3. 发布/迭代硬门槛（Gates）

每次发布（或提测）至少满足：

1) **功能正确性**：QA 按 PRD 验收标准通过  
2) **UI/交互质量**：线上测试工程师发布验证通过（含弹窗遮挡、布局、动效、点击可用性）  
3) **安全基线**：安全检查通过（框架安全项 + 依赖风险 + 数据安全）  
4) **性能基线**：性能检查通过（启动、交互、动效流畅度、包体/资源、内存/CPU）  
5) **功能完成度盘点**：自动扫描报告已更新（明确哪些按钮/功能未实现或故障）  

> 结论：QA 通过 ≠ 发布通过；构建通过 ≠ 发布通过。

### 4. Gate 的"可执行化"要求（v4.1 新增）

> Gate 必须有"证据产出物"，否则视为未执行。

| Gate | 必须产出物（至少 1 个） | 推荐责任人 |
|---|---|---|
| 功能正确性 | `docs/test-report.md`（含用例覆盖与结果） | QA |
| UI/交互质量 | `docs/release-test-report.md`（含取证） | 线上测试工程师 |
| 安全基线 | `docs/security-report.md` 或审查报告安全章节 | 审查员 / 架构师 / QA |
| 性能基线 | `docs/performance-report.md` 或发布记录性能章节 | DevOps / QA |
| 完成度盘点 | `docs/feature-scan-report.md` + 更新 `docs/feature-inventory.md` | DevOps（跑）+ 线上测试（抽检） |

### 5. Gate 执行率（v4.1 新增）

> 每个版本必须记录 Gate 执行率；执行率低于 100% 不允许宣称"发布完成"（除非用户明确批准跳过并记录原因）。

- **Gate 执行率** =（已产出证据的 Gate 数）/（应执行 Gate 数）
- 记录位置：建议写入 `docs/release-v*.md` 或 `docs/dev-notes.md` 的版本小结
- 若跳过：必须写明"跳过原因 + 风险评估 + 补偿措施 + 计划补做版本"

## 第六部分：自我进化机制 2.0（v4.1 核心增强）

> 目标：让"自我进化"从口号变成可执行闭环：**能触发 → 能验证 → 能沉淀 → 能回归检查 → 能淘汰**。

### 6.1 进化项（Evolution Item）的定义

任何"新增规则/新增流程/新增技能/新增工具/新增门槛"都必须以进化项形式登记，至少包含：

1) **触发**：是什么事件/问题触发（用户反馈、线上事故、重复缺陷、效率瓶颈等）  
2) **假设**：为什么这样做能改善（可验证的因果假设）  
3) **方案**：具体改什么（规则/流程/脚本/文档/技能）  
4) **验证方式**：怎么证明有效（指标 + 证据）  
5) **沉淀位置**：写到哪里（user_profile / docs / 项目规则 / CI / skill）  
6) **负责人**：谁负责落地与维护  
7) **状态**：提议 / 试运行 / 已启用 / 已废弃（含废弃原因）  

### 6.2 触发信号（Triggers）

触发信号分 5 类，命中任意即进入"进化项流程"：

1) **用户反馈触发**
- 正向：用户说"这样很好/保持"→ 提炼为"可复用偏好"并沉淀  
- 负向：用户说"不要这样/下次别"→ 立刻停止并沉淀为"禁止规则"

2) **重复缺陷触发**
- 同类问题在 2 个版本内出现 ≥ 2 次（例如弹窗遮挡、按钮不可点击）  
→ 必须补充：清单/Gate/自动化/组件规范四选一（优先自动化）

3) **风险事件触发**
- 出现安全相关缺陷（敏感信息泄露、越权、IPC 滥用）  
→ 必须增加：安全测试用例 + 安全审查项 + 报告模板/CI 入口

4) **性能退化触发**
- 启动/关键交互/动效流畅度明显退化，或 bundle 体积异常增长  
→ 必须增加：性能基线记录 + 回归对比 + 优化策略

5) **交付效率触发**
- 同类工作重复 ≥ 3 次（手工操作、重复排查）  
→ 必须脚本化/模板化/一键化（DevOps 或开发者负责）

### 6.3 自我进化闭环（必走 8 步）

1. **识别（Detect）**：捕捉触发信号，归类（反馈/缺陷/风险/性能/效率）  
2. **归因（Hypothesis）**：提出至少 2 个可能根因 + 选择验证路径  
3. **方案（Plan）**：定义进化项（做什么、影响范围、成本、风险）  
4. **落地（Implement）**：写规则/写流程/加脚本/加模板/加技能  
5. **证据（Evidence）**：生成证据（报告、截图 diff、扫描结果、基线数据、CI 记录）  
6. **沉淀（Persist）**：写入权威载体（见 6.4）  
7. **宣告（Announce）**：在 `docs/dev-notes.md` 记录"新增/变更内容 + 使用方式"  
8. **回归与淘汰（Review & Prune）**：按 6.7 的淘汰规则定期清理

> 关键约束：**没有证据 = 没有进化**；没有沉淀 = 不算完成。

### 6.4"该记忆就存储"——沉淀位置映射（必须遵守）

| 进化内容类型 | 应沉淀位置 | 说明 |
|---|---|---|
| 跨项目偏好/团队模式总规则 | `user_profile.md` | 最高优先级（跨项目权威） |
| 当前项目约定/执行口径 | `docs/dev-notes.md` + 需要时更新本规则树 | 项目内可追溯 |
| 代码级规范/安全红线 | 项目级规则文件（CLAUDE.md / AGENTS.md 等） | 代码层权威 |
| 可执行自动化 | 仓库脚本/CI（例如 Playwright、audit、扫描器） | 必须"一键可跑" |
| 报告与模板 | `docs/*.md` | 以模板推动落地 |
| 新能力/新工具引入记录 | `docs/dev-notes.md` 的「能力扩展」 | 记录版本/用途/状态 |

### 6.5 五维评价体系（带证据 + 权重）

**五维定义**：
1) 正确性（20%）  
2) 体验质量（20%）  
3) 安全性（25%）  
4) 性能（25%）  
5) 可维护性与交付效率（10%）

**红线规则**：
- 安全性 < 3 或 性能 < 3 → 不允许发布（除非用户批准跳过并记录风险与补偿措施）
- 正确性 < 3 → 不允许发布

**加权总分（0~100）**：`Total = Σ(W_i * S_i / 5)`

> 模板：`docs/quality-scorecard.md`

### 6.6 进化项的验收与淘汰规则（防止"规则膨胀"）

**验收（启用门槛）**：同时满足才可标记"已启用"
- 有明确触发与假设
- 有可运行入口（命令/流程）
- 有证据产出物（报告/日志/截图）
- 已写入正确沉淀位置

**淘汰/降级条件（命中任意即可进入评估）**：
- 连续 2 个版本无人执行/无证据产出
- 误报率过高（例如扫描误报导致团队不信任）
- 成本过高，投入产出不成比例
- 与更高优先级规则冲突（以 user_profile 为准）

处理方式：
- 降级为"建议项"（不再作为 Gate）
- 标记 `⚠️可能过时` 并给出替代方案
- 直接废弃，并在 dev-notes 记录原因
