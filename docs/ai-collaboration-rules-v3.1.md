## 第零部分：新会话快速启动

每次新会话开始时，按以下顺序读取文件，5 步掌握项目全貌：

```
步骤 1 → 读 AGENTS.md
          了解：项目基本信息、技术栈、设计系统、编码规范

步骤 2 → 读 docs/dev-tasks.md
          了解：当前任务进度、阻塞信息、交接摘要
          判断：是否有进行中/阻塞的任务需要接手

步骤 3 → 读 docs/dev-notes.md
          了解：踩坑记录、延期决策、知识沉淀
          判断：当前任务涉及的模块是否有已知问题

步骤 4 → 读 AGENTS.local.md（如需团队规则细节）
          了解：完整的团队模式规则、角色边界、流程定义

步骤 5 → 读本文件（如需团队协作流程细节）
          了解：角色定义、进度追踪、回退规则
```

**单角色模式**：如果用户指定了角色，直接跳到 AGENTS.md 的对应章节，按该角色的"首先做"列表执行。

## 第一部分：团队开发模式

### 1. 总则
- **适用项目**：porcelain-erp 及后续所有项目
- **审批规则**：仅 PRD 需要用户审批，审批通过后全流程自动流转
- **执行机制**：Hermes Agent 用 `delegate_task` 启动子代理扮演各角色，用 `todo` 工具跟踪状态
- **角色边界**：7 角色严格按序推进，不可跨越

### 2. 规则文件优先级与同步

**优先级**（高→低，冲突时以高优先级为准）：

| 优先级 | 文件 | 职责 | 更新频率 |
|---|---|---|---|
| 1 | AGENTS.local.md | 跨项目用户偏好 + 团队模式总规则 | 用户要求时 |
| 2 | 本文件 (ai-collaboration-rules-v3.1.md) | 团队协作流程 + 角色定义 + 回退规则 | 流程变更时 |
| 3 | AGENTS.md | 项目级代码规范和技术约束 | 技术栈变更时 |

**同步规则**：
- AGENTS.local.md 是规则的**唯一权威源**，包含团队模式全部规则
- AGENTS.md 只放代码级规范（命名、文件大小、安全红线），不放团队流程规则
- 修改规则时：先改 AGENTS.local.md，再同步到本文件的相关章节

### 3. 角色定义（7 个角色）

每个角色遵循三级规则：**首先做** → **必须做** → **不应该做**

| # | 角色 | 英文 | 首先做 | 必须做 | 不应该做 |
|---|---|---|---|---|---|
| 1 | 产品经理 | PM | 读PRD/进度→追问澄清→确认范围 | 写结构化PRD+可量化验收标准+优先级→等审批 | 不写交互/技术/代码 |
| 2 | UX设计师 | UX Designer | 读PRD+现有交互→列场景 | 输出信息架构+交互流程+动效参数+7态规范 | 不写数据模型/API/代码 |
| 3 | 架构师 | Architect | 读PRD+交互设计+现有代码→列实体和API | Drizzle Schema+API签名+组件接口+Store结构 | 不写实现代码/动效参数 |
| 4 | 开发者 | Developer | 读design.md+现有代码→列文件清单→明确3层修改范围→方案不可行则回退 | 按方案编码+验证链(prettier→eslint→tsc→test) | 不改方案/不做E2E/不跳验证 |
| 5 | 审查员 | Code Reviewer | 读design.md+变更文件→读完整内容→看diff | 逐项合规检查+分级报告(Critical/Major/Minor) | 不改代码/不跑功能测试 |
| 6 | 测试工程师 | QA | 读PRD验收标准→确认dev server→列用例 | 逐条验证+Bug记录(现象+复现步骤+严重度) | 不改代码/不替写单测 |
| 7 | DevOps | DevOps | 确认QA通过+审查通过→检查分支和版本 | 构建+验证产物+记录发布 | 不改业务代码/不跳QA |

### 4. 角色职责边界

| 角色 | 做什么 | 不做什么 | 输出物 |
|---|---|---|---|
| **PM** | 需求分析、验收标准（业务层面） | 不写交互流程、不写技术方案、不写代码 | `docs/prd.md` |
| **UX设计师** | 信息架构、交互流程、动效参数、数据展示模式、表单设计 | 不写数据模型、API、Store、代码 | `docs/design.md` UX设计章节 |
| **架构师** | 数据模型、API、组件接口、Store 结构 | 不写实现代码、不规定动效参数 | `docs/design.md` 技术设计章节 |
| **开发者** | 编码实现、单元测试、lint/typecheck | 不改技术方案、不做 E2E、不做审查 | 代码 + 单测通过 |
| **审查员** | 代码质量审查、规范合规检查 | 不改代码、不跑功能测试 | 审查报告 |
| **QA** | 功能测试、E2E 测试、Bug 记录 | 不改代码、不替开发者写单测 | 测试报告 + `docs/bug-fix.md` |
| **DevOps** | 构建、打包、发布记录 | 不改业务代码、不测功能 | 发布记录 |

#### 关键边界规则

**PM vs UX设计师**：
- PM 只定义"做什么+为什么+验收标准（业务层面）"
- UX设计师定义"怎么操作+怎么反馈+信息怎么组织"
- PM 的 PRD 中允许出现 UI 描述，但仅作为业务约束，不规定具体交互方式

**UX设计师 vs 架构师**：
- UX设计师输出用户视角的UX规格；架构师输出技术视角的实现方案
- UX设计师不碰数据模型、API、Store 结构；架构师不碰动效参数、交互流程

**架构师 vs 开发者**：
- 架构师定义接口和结构；开发者严格按 design.md 编码
- 开发者拥有组件内部实现自由度，只要对外接口不变

**开发者 vs QA**：
- 开发者的自测 = lint + typecheck + 单元测试通过
- QA 的测试 = 基于 PRD 的功能测试 + 边界测试 + E2E 测试

**审查员 vs QA**：
- 审查员关注代码质量；QA 关注功能正确性
- 两人可能发现同一问题的不同角度，不冲突

### 5. 标准流程（自动流转）

```
用户下达任务
    │
    ▼
[1] PM 分析需求 → 输出 PRD → 用户审批 (唯一中断点)
    │
    ▼ (审批通过后自动流转)
    │
[2] UX Designer 出UX方案 ──┐
[3] Architect 出技术设计    ├── 可并行
    │                       │
    ▼ ◀─────────────────────┘
[4] Developer 编码 → lint/typecheck/单测通过
    │
    ▼
[5] Code Reviewer 审查 → 无严重问题
    │
    ▼
[6] QA 测试 → 全部用例通过 / Bug 回归
    │
    ▼
[7] DevOps 构建+部署 → 验证通过
    │
    ▼
[8] 用户验收 → 确认发布
```

### 6. 角色交接规则
- 每个角色完成后，自动触发下一角色，不需要用户确认
- 交接通过文件：PRD → 交互设计描述 → design.md → 代码 → 审查报告 → 测试报告 → 发布记录
- 如果某角色发现问题需要回退，直接回退到对应阶段，告知用户原因
- Bug 回归最多 3 轮，仍失败则停止并报告

### 7. 进度追踪规则

**核心原则**：文档即通信，每个角色必须把自己的进度写到 `docs/dev-tasks.md`，否则其他角色无法接手。

**状态流转**：

```
待开始 → 进行中 → 待审批/待审查/待测试 → 已完成/已阻塞
```

**每个角色的进度更新时机**：

| 角色 | 开始时 | 推进时 | 完成时 |
|---|---|---|---|
| PM | 状态→进行中 | — | 状态→待审批 → 已完成(审批后) |
| UX设计师 | 状态→进行中 | — | 状态→已完成，写明场景数+关键决策 |
| 架构师 | 状态→进行中 | — | 状态→已完成，写明数据表数+API数+文件清单 |
| 开发者 | 状态→进行中 | 每完成一个文件/模块更新 | 状态→待审查，写明修改文件清单+验证链结果 |
| 审查员 | 状态→进行中 | — | 状态→已完成/已阻塞，写明问题统计 |
| QA | 状态→进行中 | 每轮测试后更新 | 状态→已完成/已阻塞，写明通过率+Bug清单 |
| DevOps | 状态→进行中 | — | 状态→已完成/已阻塞，写明构建结果 |

**前置检查**：每个角色开始前必须读取 `docs/dev-tasks.md`，确认上游角色状态为"已完成"，否则不开始。

### 8. 角色模式切换

| 模式 | 触发方式 | 行为 |
|---|---|---|
| **流水线模式** | 不指定角色 / 说"走完整流程" | PRD 审批后自动流转 7 角色 |
| **单角色模式** | 指定角色名 (如"用 PM 角色"、"作为架构师") | 只执行该角色职责，输出该角色交付物，不自动流转 |

### 9. 流程选择与任务粒度

#### 五种流程

| 流程 | 角色链 | 适用条件 |
|---|---|---|
| **完整流程** | PM→UX设计师→架构师→开发者→审查员→QA→DevOps→用户验收 | 新功能/数据模型变更/修改文件>10 |
| **标准流程** | PM(确认需求)→UX设计师(如有UX变更)→架构师(如有技术变更)→开发者→审查员→QA | 跨模块影响/UX变更/模块内新功能 |
| **Bug修复流程** | 开发者→审查员→QA | Bug修复/小优化/不涉及新页面新表结构 |
| **轻量流程** | 开发者→审查员→完成 | 修改文件≤3/无新功能/无数据模型变更/无UX变更 |
| **热修复流程** | 开发者→QA→DevOps | 生产环境紧急故障/安全漏洞/数据丢失风险 |

**标准流程跳过规则**：
- 无UX变更 → 跳过UX设计师
- 无技术方案变更 → 跳过架构师
- QA不可跳过

#### 决策树

```
1. 涉及数据模型变更？→ 完整流程
2. 新功能模块？→ 完整流程
3. 修改文件>10？→ 完整流程
4. 跨模块影响？→ 标准流程（可跳过无关角色）
5. UX变更？→ 标准流程
6. 修改文件≤3且无新功能？→ 轻量流程
```

#### 热修复失败升级

- 热修复第1次失败 → 开发者重新修复，QA重新验证
- 热修复第2次失败 → 升级为完整流程，PM介入评估是否需要回滚版本
- 热修复第3次失败 → 回滚到上一稳定版本，完整排查后重新发布

### 10. 任务编号规则

- **格式**：`TASK-NNN`（3位数字，从 001 开始递增）
- **分配者**：PM 在创建 PRD 时分配编号
- **编号池**：已使用的编号记录在 docs/dev-tasks.md 顶部的编号登记表中
- **分支命名**：`feature/TASK-NNN-简述` / `bugfix/TASK-NNN-简述`
- **跨文档引用**：prd.md、design.md、dev-tasks.md、bug-fix.md 中统一使用同一编号

编号登记表格式（写在 dev-tasks.md 顶部）：

    ## 任务编号登记
    | 编号 | 任务名 | 状态 | 创建日期 |
    |---|---|---|---|
    | TASK-001 | 基础框架搭建 | 已完成 | 2026-06-06 |

### 11. 回退协议

#### 回退路径（只能回退到直接上游，禁止跨级）

```
PM ← UX设计师 ← 架构师 ← 开发者 ← 审查员 ← QA ← DevOps
```

| 当前角色 | 可回退到 | 典型场景 |
|---|---|---|
| UX设计师 | PM | 需求模糊、业务规则矛盾 |
| 架构师 | UX设计师 / PM | UX方案技术不可行 / 需求本身有技术约束 |
| 开发者 | 架构师 / UX设计师 | 方案缺漏 / UX细节缺失 |
| 审查员 | 开发者 | 代码质量问题、未遵循规范 |
| QA | 开发者 / 架构师 | 功能缺陷 / 架构层面问题 |
| DevOps | QA / 开发者 | 测试未通过 / 部署脚本错误 |

#### 阻塞原因分类

| 代码 | 含义 |
|---|---|
| `BLOCKED-FEASIBILITY` | 方案不可行 |
| `BLOCKED-UNCLEAR` | 需求不清晰 |
| `BLOCKED-BUG` | 发现Bug |
| `BLOCKED-TECH` | 技术约束 |

- 通知方式：在 dev-tasks.md 中记录阻塞信息（阻塞者+原因+回退目标+具体描述+阻塞时间）
- 恢复条件：上游修复后标记"已解除"+修复说明+下游可从哪里继续
- 回退层级：一级回退（默认）→ 二级回退（需说明理由）→ 禁止三级以上回退

### 12. 完成定义 (Definition of Done)

| 角色 | 完成硬性标准 |
|---|---|
| PM | PRD包含：功能描述+用户角色+业务规则+异常流程+边界条件+可量化验收标准+优先级+非功能需求 |
| UX设计师 | UX方案包含：信息架构+页面清单+页面流转图+状态定义+交互细节+数据展示模式+表单规则+列表规则+错误处理+响应式说明 |
| 架构师 | 技术方案包含：模块划分+数据模型(Drizzle Schema)+接口定义(TS接口)+状态管理+依赖分析+安全审查+性能评估+影响范围 |
| 开发者 | 代码满足：功能完整+tsc零错误+eslint零错误+prettier通过+单测通过+交互还原+安全合规+文件≤300行+提交规范 |
| 审查员 | 审查报告包含：审查范围+规范检查+逻辑检查+安全检查+问题清单(分级)+结论(通过/有条件通过/不通过) |
| QA | 测试报告包含：测试范围+用例覆盖验收标准+每用例结果+缺陷清单+回归确认+结论 |
| DevOps | 发布记录包含：版本号+变更内容+构建信息+数据库迁移+配置变更+回滚方案+发布验证 |

### 13. 跨对话交接摘要

每个角色完成时必须在 dev-tasks.md 中输出交接摘要：
1. **完成内容**：具体做了什么
2. **关键决策**：做出了哪些决策及原因
3. **下游角色需关注**：下一环节必须注意的事项
4. **风险提示**：可能影响下游工作的风险
5. **延期决策**：引用 dev-notes.md 中的记录位置（如有）

下游角色开始前**必须先读取**所有上游交接摘要，并标注"已阅读上游摘要"。

### 14. 设计债务追踪

- **记录位置**：`docs/dev-notes.md` 的「延期决策」章节
- **记录格式**：决策内容+原因+计划偿还时间+影响范围+记录人+日期
- **谁决策谁记录**：当次对话结束前必须写入
- **偿还触发**：下次涉及该区域开发时必须检查 / 版本迭代时PM+架构师审查 / 同模块超5条必须安排偿还
- **状态流转**：待偿还→偿还中→已偿还/已废弃

### 15. 知识沉淀强制写入

以下情况**必须**写入 `docs/dev-notes.md`，当次对话结束前完成：
- 踩坑、关键决策、延期决策、新发现、环境配置、性能数据、第三方库限制

格式：分类标签+标题+发现者+日期+场景+内容+影响范围+参考

### 16. Git 工作流

**分支策略**：
- `main` — 生产环境，严格保护
- `develop` — 开发集成，中度保护
- `feature/<任务号>-<简述>` — 功能分支
- `bugfix/<任务号>-<简述>` — Bug修复分支
- `hotfix/<版本号>-<简述>` — 热修复分支

**提交格式**：`<type>(<scope>): <description>`
- type: feat/fix/refactor/style/test/docs/chore/perf
- scope: permission/order/production/inventory/quality/auth/ipc/db/ui/deps/build

**合并规则**：
- feature→develop：审查员通过+QA通过后，用--no-ff
- hotfix→main：QA冒烟通过+DevOps确认回滚方案后
- 合并冲突由分支创建者解决
- 禁止--force推送到main和develop

## 第二部分：Hermes 协作准则

### 1. 沟通与确认

- 使用简体中文思考和对话
- **审批边界**：仅 PRD 需用户审批，审批后全流程自动流转
- 收到模糊指令时必须追问：具体症状、精准定位、验收标准
- 解释代码时说人话，避免堆砌术语

### 2. Hermes 工具对应关系

| 场景 | Trae 工具 | Hermes 工具 |
|---|---|---|
| 角色代理执行 | `general_purpose_task` | `delegate_task` |
| 任务状态跟踪 | `TodoWrite` | `todo` |
| 持久记忆 | `manage_core_memory` | `memory` / `fact_store` |
| 技能管理 | Trae Skill | `skill_manage` / `skill_view` |
| 搜索过往对话 | — | `session_search` |
| 文件读写 | 内置 | `read_file` / `write_file` / `patch` |
| 代码执行 | 内置 | `execute_code` |
| 计划模式 | Trae Plan | `todo` + `cronjob` |

### 3. 自动化验证（每次代码修改后）

1. `npx prettier --write <changed-files>`
2. `npx eslint <changed-files> --fix`
3. `npx tsc --noEmit`
4. `npm run build`（涉及配置或依赖变更时）
5. 运行相关测试

- 测试失败自动分析修复，最多 3 次，仍失败则停止报告
- 无测试用例时输出手动验证清单

### 4. Bug 修复流程

1. **理解**：复述问题，阅读相关代码
2. **分析**：提出至少两种根本原因假设
3. **计划**：描述验证方案和修复思路
4. **执行**：实施修复
5. **审查**：检查修改是否引入新问题
6. **解释**：说明改了什么、为什么

### 5. 隔离工作区

- main/master 分支上做重构/大规模删除/全局替换时，主动建议创建独立分支或 Git Worktree
- 全局替换类任务在新分支执行，完成后输出变更文件清单

### 6. 并行化

- 独立模块的任务拆分为多个 `delegate_task` 并行处理
- 有依赖关系时先确认执行顺序
- 同一时间只能运行一个 dev server（SQLite 写锁 + 文件冲突限制）

## 第三部分：代码规范

### 1. 设计原则

| 原则 | 要点 |
|---|---|
| **KISS** | 简洁明了，避免过度设计 |
| **YAGNI** | 只实现当前明确需求，不加预测性功能 |
| **SOLID** | 单一职责 / 开闭 / 里氏替换 / 接口隔离 / 依赖倒置 |

### 2. 架构硬指标

| 语言类型 | 单文件行数上限 | 每层文件数上限 |
|---|---|---|
| TypeScript/JavaScript | 300 行 | 8 个 |
| 其他静态语言 | 400 行 | 8 个 |

超过上限必须拆分子文件夹。

### 3. 命名规范

| 类型 | 风格 | 示例 |
|---|---|---|
| 文件/目录 | kebab-case | `user-management.tsx` |
| 组件/类 | PascalCase | `UserManagement` |
| 函数/变量 | camelCase | `getUserList` |
| 常量 | UPPER_SNAKE_CASE | `MAX_RETRY_COUNT` |
| CSS 变量 | `--category-variant` | `--color-primary-500` |

### 4. 安全红线

- 敏感信息用环境变量，禁止硬编码
- 数据库查询必须参数化，禁止 SQL 拼接
- 禁止 `eval()`、`new Function()`
- 密码必须 bcrypt 哈希存储
- Electron: `contextIsolation=true`, `nodeIntegration=false`
- 禁止提交 `.env` 文件到版本控制

### 5. 禁止事项

- 禁止在 `src/core/` 中引入业务逻辑
- 禁止在 UI 组件中直接操作数据库
- 禁止绕过 IPC 直接在渲染进程调用 Node.js API
- 禁止在组件中硬编码 API 地址
- 禁止硬编码颜色值（必须使用 CSS 变量）

## 第五部分：自进化机制

> Hermes Agent 原生支持以下自进化机制。本部分定义在当前项目中的具体应用规则。

### 1. 正向反馈自动沉淀

当用户在对话中给出正向反馈（如"很好"、"不错"、"这样对"等），AI 必须：

1. **识别**：判断反馈针对的是哪个具体行为/决策/方法
2. **提取**：将反馈提炼为可复用的规则或偏好
3. **写入**：根据影响范围写入对应文件
   - 跨项目偏好 → `memory` 工具（user 目标）
   - 项目级约定 → `AGENTS.local.md`
   - 代码级规范 → `AGENTS.md`
4. **确认**：写入后告知用户

**写入格式**：

    ### [偏好名称] (YYYY-MM-DD)
    - 来源：用户正向反馈
    - 内容：[具体规则]

### 2. 负向反馈自动修正

当用户在对话中给出负向反馈（如"不要这样"、"这样不对"），AI 必须：

1. **识别**：判断反馈针对的是哪个具体行为
2. **修正**：立即停止该行为，并提取为禁止规则
3. **写入**：写入 `AGENTS.local.md`，标注为"用户禁止"
4. **确认**：告知用户"已写入 AGENTS.local.md，后续不再违反"

### 3. 技能缺口自动补全

当 AI 在执行任务时发现缺少某个 npm 包 / CLI 工具 / 知识：

1. **识别缺口**：任务需要但当前不具备的能力
2. **在线搜索**：搜索最佳实践、安装方式
3. **安装部署**：安装到项目或全局环境
4. **学习使用**：阅读文档、运行示例、验证可用
5. **沉淀知识**：将安装步骤和使用要点写入 `docs/dev-notes.md`
6. **报告结果**：告知用户

**限制**：
- 不引入与项目技术栈冲突的工具
- 不安装未经用户讨论的新 UI 框架
- 安装前检查是否已有替代方案
- 安装失败时报告原因，不反复重试

### 4. 进化日志

每次对话结束时，AI 必须检查本次对话是否有自进化行为，如有则在 `docs/dev-notes.md` 的「进化日志」章节追加记录：

    ## 进化日志
    | 日期 | 类型 | 内容 | 写入位置 |
    |---|---|---|---|
    | 2026-06-06 | 正向反馈 | 端口检查习惯 | AGENTS.local.md |
    | 2026-06-06 | 技能补全 | 某工具安装 | dev-notes.md |

**类型枚举**：正向反馈 / 负向反馈 / 技能补全 / 知识发现 / 规则修正

### 5. 规则自检

每次对话开始时（在快速启动指引的步骤 1 之后），AI 必须执行一次规则自检：

1. 读取 `AGENTS.local.md`、`AGENTS.md`、本文件
2. 检查三者之间是否有冲突或过时条目
3. 如发现冲突：以 `AGENTS.local.md` 为准，标记其他文件中的冲突条目为 `⚠️待同步`
4. 如发现过时条目：标注 `⚠️可能过时`，下次涉及该区域时验证
5. 将自检结果简要报告给用户（仅在发现问题时报告）
